Couple — V3 connectée

Cette version transforme le prototype local en application à deux appareils. Elle nécessite un projet Supabase avant la première utilisation réelle.

1. Créer le projet Supabase

  1. Créer un projet Supabase.
  2. Ouvrir SQL Editor.
  3. Copier l’intégralité de supabase/schema.sql puis l’exécuter.
  4. Vérifier dans les réglages Realtime que le service Realtime est activé. Le script ajoute déjà vouchers à la publication supabase_realtime.

2. Configurer l’authentification

  1. Dans Authentication → Sign In / Providers, conserver Email activé.
  2. La confirmation d’e-mail peut rester activée — c’est recommandé.
  3. Dans Authentication → URL Configuration, définir le Site URL sur l’URL GitHub Pages finale de Couple.
  4. Ajouter également cette URL exacte aux Redirect URLs.
Important : le lien de confirmation doit revenir vers l’URL réelle de l’application, et non vers localhost.

3. Renseigner la connexion publique

Dans les réglages/API du projet, récupérer l’URL Supabase et la clé publishable (ou l’ancienne clé anon).

Ouvrir config.js :

window.COUPLE_CONFIG = {
  url: "https://VOTRE-PROJET.supabase.co",
  key: "VOTRE_CLE_PUBLISHABLE"
};
Ne jamais utiliser la clé service_role. Elle contourne les règles de sécurité et ne doit jamais être placée dans une application web.

4. Publier sur GitHub Pages

Mettre à jour le dépôt en conservant la structure :

index.html
config.js
manifest.webmanifest
sw.js
icons/
  icon-180.png
  icon-192.png
  icon-512.png
  icon-maskable-512.png

5. Créer votre couple

  1. Premier téléphone : créer un compte, confirmer l’e-mail si demandé, puis choisir Créer notre espace.
  2. Partager le code temporaire affiché.
  3. Xiaomi : ouvrir la même URL, créer le second compte et choisir Rejoindre mon partenaire.
  4. Saisir le second prénom et le code.
  5. Une fois liés, les deux téléphones utilisent le même Carnet.

6. Installer l’application

iPhone : Safari → Partager → « Sur l’écran d’accueil ».

Xiaomi / Android : Chrome → « Installer l’application » ou « Ajouter à l’écran d’accueil ».

7. Test avant les vrais bons

  1. Envoyer un bon test.
  2. Vérifier que le destinataire voit uniquement qu’un bon est arrivé avant découverte.
  3. Vérifier qu’avant découverte il ne reçoit ni titre, ni message, ni catégorie, ni date exceptionnelle initiale.
  4. Découvrir et gratter le bon.
  5. Tester proposition de date, validation, refus et annulation sur les deux téléphones.
  6. Tester un privilège annuel et les compteurs annuels.

Sécurité fonctionnelle

Les données révélatrices sont stockées dans voucher_secrets. Le destinataire ne peut pas lire cette ligne avant d’avoir choisi de découvrir le bon. Les mutations importantes passent par des fonctions serveur et les tables sont protégées par RLS.

Limites de cette étape

  • Pas encore de notification push lorsque l’application est complètement fermée.
  • Synchronisation temps réel quand l’application est ouverte, plus resynchronisation au retour au premier plan et périodiquement.
  • Pas de migration automatique des anciennes données locales de démonstration.
  • Le projet Supabase et le SQL doivent être configurés une fois manuellement.
Conseil : faites d’abord tout le parcours avec deux bons fictifs. Une fois validé, repartez avec des comptes définitifs et une base propre.
